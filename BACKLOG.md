- `first-glance-clarity: intentTier--danger vs base color converge under red-green color-vision deficiency` — new finding while re-verifying the above fix. - `beat:boss-telegraph mechanism:guard-pitch-contour` — low-priority nuance flagged by `game-dopamine-evaluator`'s qualitative pass, evaluated here from a presentation-correctness angle and considered worth tracking (not urgent): the `guard` cue's two-tone sequence is descending (262Hz → 196Hz), which in typical game-audio convention reads as "negative/fail" (e.g. a miss or death stinger — this game's own `playEndGameSting(false)` uses a descending sawtooth triple for death), while ascending tones read as "positive/success" (the win sting is ascending). `guard` means "safe, zero incoming damage this turn" — the opposite of what a descending contour conventionally signals — so on a player's *first* exposures (before they've learned by repetition that low+descending=guard=harmless here), the pitch direction alone could momentarily misread as bad news. Confirmed the color channel (`.intentAlert--safe` blue `#80d8ff` vs `.intentAlert--danger` red/orange `#ff6e40`) already disambiguates unambiguously and passes WCAG AA per `game-usability-tester`'s check, so this is not a blocker — just a case where the audio-alone signal fights the color-alone signal on convention. Suggested (cheap, no new dependencies): flip `guard`'s tone order to ascending (e.g. 196Hz→262Hz, same frequencies, reversed order) so both channels agree in the "safe" direction; verify `charge`'s existing 660→880 ascending order still reads as danger via its color tint doing the disambiguating work there instead (rising pitch is more ambiguous for danger than for safety, but charge already leans on its red tint + higher absolute pitch + square-wave harshness, so it's lower-risk as-is).
- `mechanism:haptics` — `navigator.vibrate` is never used anywhere in the codebase, despite the game being touch-first/mobile-primary. Re-verified 2026-07-23 (grep for `vibrate` across `game.js`/`index.html`: zero matches), still absent. Suggested: `navigator.vibrate(ms)` guarded by a feature check, alongside the existing `flashHit`/`playEndGameSting`/`announceIntent` call sites (routine hit / lethal hit / win / death / boss telegraph).
- `beat:near-lethal mechanism:severity-undifferentiated` — new finding 2026-07-23. `flashHit()`'s `lethal` flag (which swaps the beep to the low 160Hz sawtooth tone) only fires when `state.player.hp <= 0` exactly (`game.js` lines ~541, ~559); a hit that drops the player to e.g. 1/33 HP (well under the `hpTier--danger` <25% threshold already used for the HP-bar recolor at line ~651) plays the *exact same* routine-hit cue (440Hz square beep, `hitShake` 6px/0.3s, `brightness(1.6)` flash) as a hit that does trivial chip damage at full HP — verified via Playwright by setting `state.player.hp = 5` and confirming `renderBattle()` only toggles the static (non-animated) `hpTier--danger` HP-bar class, with no distinct sound/shake/haptic tied to the near-death threshold itself. This is the single biggest gap against this evaluator's own priority beat (near-lethal hit on the player) — a life-threatening moment currently reads identically to a routine poke unless it happens to be the literal killing blow. Suggested: in the two `flashHit('battlePlayer', ...)` call sites, compute a `nearLethal = state.player.hp > 0 && state.player.hp / state.player.maxHp < 0.2` alongside the existing `lethal` check, and give it its own escalated cue — e.g. a distinct mid-register sawtooth/square beep between the routine and lethal tones, a `navigator.vibrate([...])` pulse (ties into the haptics gap above), and/or a brief screen-edge red vignette — so survival-by-a-thread actually feels different from a shrug-off hit.
- `beat:hit/lethal-enemy/lethal-player mechanism:shake-flash-not-severity-scaled` — new finding 2026-07-23. `flashHit()` (`game.js` ~line 109) applies the identical `hitFlash` class (fixed `hitShake` keyframe: 6px max `translateX`, 0.3s; fixed `brightness(1.6) drop-shadow` flash, `index.html` ~line 157-169) regardless of damage dealt or HP remaining — only the accompanying tone (440Hz square vs 160Hz sawtooth) differs, and only for the exact `hp<=0` tick. A chip-damage card and a floor-clearing overkill blow, or a doubled-damage `chargeBonus` boss attack that leaves the player at 1 HP, all shake/flash the battle portrait by the same fixed amount. Confirmed via Playwright (`getComputedStyle` on `#battleEnemy`/`#battlePlayer` immediately after triggering hits of different sizes: `animationName`/`filter` values are identical strings regardless of `dmg`). Suggested: scale shake amplitude/duration or flash brightness by `dmg / maxHp` (or by the lethal/near-lethal tiers above) so a killing or near-killing blow visibly hits harder than a routine one — cheap, no new dependencies, just parameterizing the existing keyframe via a CSS custom property or a second `hitFlash--heavy` class variant.
