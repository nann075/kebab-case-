# Backlog

Durable, cumulative index of findings that evaluators deliberately left
unfixed (medium-severity / judgment-call items, not urgent enough to fix
the cycle they were found in). Maintained by `game-usability-tester` and
`game-feel-evaluator`, each owning their own section below. `game-idea-
agent` reads this as a primary source when researching what to propose
next. See each agent's `.claude/agents/*.md` for the maintenance rules.

## game-usability-tester

- `touch-target: #endTurnBtn/#skipRewardBtn/#removeCardBtn/#skipBuffBtn under 40px` — all measured at 36px tall (shared `padding: 8px 22px; font-size: 14px` button rule), under the ~40px guideline. Width/spacing are fine, this is a height-only shortfall. Re-verified 2026-07-22 (endTurnBtn measured 116.7x36px, restart/title overlay buttons measured 40.7px tall — closer but still just under — at iPhone-16e viewport): still accurate.
- `legibility: .cardDesc at 9.5px` — card description text renders just under the ~10-11px comfort floor; hand container has vertical headroom for a small bump. Re-verified 2026-07-22: still 9.5px, unchanged.
- `legibility: disabled-card contrast ~2.36-2.91:1` — `.card.disabled { opacity: 0.4 }` composited over `#111` drops name/desc text contrast well below WCAG AA's 4.5:1, on already-small text. Consider dimming only the border/background instead of the text, or a smaller opacity drop (~0.6). Re-verified 2026-07-22 (recomputed: name 2.91:1, desc 2.36:1 against the composited card background): still accurate.
- `interaction-consistency: pointerdown vs click` — all card elements (hand/reward/buff/remove-deck, 4 sites) use `pointerdown`; every standalone button (10 listeners: end turn, restart, title, skip reward, remove-card, cancel-remove, skip buff, 3x difficulty select) uses `click`. Buttons fire a beat later (on release) than cards (on touch-start). Re-verified 2026-07-22, still accurate (listener count unchanged at 10).
- `decision-visibility: #hand gap 6px` — hand-card gap is 6px, inconsistent with the 12px used on reward/buff/remove-deck card rows; `#hand`'s reserved `min-height: 214px` has headroom to match. Re-verified 2026-07-22: still 6px vs 12px, unchanged.
- `decision-visibility: player HP has no urgency cue` — `#battlePlayerHp` renders in the same cyan regardless of HP%, and there's no bar for the player (only the enemy gets a `.hpBarInner` red bar). A player can't tell "am I in danger" from color/shape alone at a glance. Re-verified 2026-07-22 via side-by-side screenshots at 26/26, 4/26, and 4/26+20 block — all three states are visually identical except for the digits themselves; still accurate.
- `decision-visibility: #battleEnemyIntent actionType tint is pulse-only, reverts to shared neutral color` — commit 0b98889 added `.intentAlert--danger` (`#ff6e40`, charge) and `.intentAlert--safe` (`#80d8ff`, guard) on top of the existing `.intentAlert` yellow (`#fff59d`, attack); confirmed via Playwright these three are visually distinct from each other and pass WCAG AA against the `#111` app background (contrast 6.79:1 / 11.86:1 / 16.90:1 respectively — all comfortably above 4.5:1). However, `announceIntent()` removes all three alert classes again after a `scheduleTimer(..., 400)` (confirmed empirically: color read back `rgb(255,110,64)` at t=0 and `rgb(255,183,77)` — the plain `#battleEnemyIntent { color: #ffb74d }` base — at t=500ms). The base resting color is identical amber/orange for all three `actionType`s, so the color differentiation is only present for the 400ms pulse at the moment the intent is revealed (which also coincides wall-clock with the `hitShake`/`flashHit` animation from the attack that just resolved, competing for attention), not for the rest of the turn while the player is actually deciding which cards to play against that intent — which is when the color cue would be most useful, since the text label is legible but color is a faster glance-parse. Suggest making the tint persistent for as long as that intent is current (e.g. set `#battleEnemyIntent`'s resting `color`/`text-shadow` per `actionType` in `renderBattle()`, in addition to the existing pulse-on-reveal), not just flashing it.

## game-feel-evaluator

- ~~`beat:boss-telegraph mechanism:none`~~ — FIXED (commits 8f60e40, 5a40dbc). `announceIntent()` now fires on every boss-intent reveal: `.intentAlert` class drives a 0.4s `intentPulse` scale animation + `#fff59d` color/text-shadow on `#battleEnemyIntent`, and `playIntentAlertSound()` plays a distinct two-tone sine beep (330Hz→494Hz), sequenced 120ms after the hit beep so they don't collide. Re-verified 2026-07-22 via Playwright: forcing a boss floor + `announceIntent()` confirmed `getComputedStyle(el).animationName` goes `none` → `intentPulse` synchronously on call and the `.intentAlert` class self-clears after the 400ms window. Entry pruned.
- `beat:boss-telegraph mechanism:audio-undifferentiated` — the alert cue added in 8f60e40 (two-tone sine beep + `.intentAlert` pulse) is identical regardless of `enemy.actionType`; confirmed in code (`playIntentAlertSound()` takes no type param, and the `game.js` comment above the `announceIntent`/`playIntentAlertSound` block explicitly notes tone-per-type differentiation was deferred: "種別ごとの音色分けは将来の拡張課題"). This matters because the three telegraphed outcomes have very different stakes: `charge` (2x damage next hit — real threat, confirmed via `guard-decision-check.js`/dopamine-evaluator findings) vs `attack` (normal damage) vs `guard` (enemy doesn't attack that turn at all — zero damage to player, per `game.js` `enemyBattleAttack()` guard branch, which only logs and deals no hit). Firing the same "pay attention" cue for a high-stakes reveal and a no-stakes reveal risks alert fatigue and undercuts the charge cue's signal value on repeat playthroughs — flagged originally by `game-dopamine-evaluator`'s qualitative pass, and it holds up from a presentation-correctness angle too: the cue should let a player react by ear/glance alone, and currently can't. Suggested: differentiate by `actionType` — e.g. keep the current cue for `attack`, use a sharper/higher rising tone + warmer (red/orange) pulse tint for `charge` (danger, block up), and a lower/calmer tone + cool (blue/green) tint for `guard` (safe, no incoming damage this turn). No new dependencies — same `playBeep`/`.intentAlert`-class technique, just parameterized by type.
- `mechanism:haptics` — `navigator.vibrate` is never used anywhere in the codebase, despite the game being touch-first/mobile-primary. Re-verified 2026-07-22 (grep for `vibrate|navigator` across `game.js`/`index.html`: zero matches), still absent. Suggested: `navigator.vibrate(ms)` guarded by a feature check, alongside the existing `flashHit`/`playEndGameSting`/`announceIntent` call sites (routine hit / lethal hit / win / death / boss telegraph).
