- `first-glance-clarity: intentTier--danger vs base color converge under red-green color-vision deficiency` — new finding while re-verifying the above fix. Simulated deuteranopia/protanopia (standard RGB approximation matrices) on the three intent colors: base attack `#ffb74d` and danger `#ff6e40` are both amber/orange and land close together after simulation (Euclidean distance ~46 in simulated RGB) versus their distance from safe `#80d8ff` (~169-179) — i.e. `guard`(safe/blue) stays clearly distinct, but a colorblind player relying on color alone would have a much harder time telling "boss is charging/about to hit twice as hard" (danger) apart from "boss is about to do a normal attack" (base/no tint) at a glance, which is exactly the higher-stakes distinction this feature exists to telegraph. The text label (`次のターン: 溜めている(次は2倍ダメージ)` vs `次の攻撃: Nダメージ`) still fully disambiguates so no information is lost, just the fast glance-parse color shortcut is weak for this specific pair. Consider a secondary non-color cue for the danger tier specifically (e.g. bold weight, an icon/prefix like "⚠", or the existing pulse animation replaying periodically while charge is active) so color-vision-deficient players get the same at-a-glance urgency signal sighted players do.
- `interaction-consistency: 250ms overlay-input-guard silently swallows sub-250ms real taps with no distinguishing feedback` — new finding this cycle (`armOverlayInputGuard`/`isOverlayInputGuarded`, `game.js` ~line 55-70, added to prevent the last-kill-tap from bleeding into the reward/buff/event overlay that pops in under the same coordinates). Verified via Playwright with real trusted `page.mouse.click()` (not synthetic `dispatchEvent`, which the guard correctly exempts via `e.isTrusted`): a single real tap on a reward card at 150ms or 200ms after the overlay appears is fully swallowed (no deck change, mode stays `reward`), while 250ms+ registers normally — the cutoff is exact and matches the `OVERLAY_INPUT_GUARD_MS` constant. The guard's actual target scenario (accidental double-tap in the same spot, e.g. two real clicks 30-150ms apart, both still inside the 250ms window from overlay-show) is confirmed fully absorbed with zero accidental picks — the feature works as designed and does not affect `tools/playtest.js`'s bot (untrusted events bypass it entirely, confirmed via code + a synthetic-click check). The friction: a swallowed tap gives no dedicated feedback (no log line, no sound, no `navigator.vibrate`) — only the pre-existing `.card:active { transform: scale(0.96) }` CSS press-state, which fires on any pointerdown regardless of whether the JS handler acted on it, so a player whose first tap lands in the 150-200ms range experiences a card that visually depresses but does nothing, then has to tap again with no explanation why. Reaction-time context: genuinely reading 3 new cards and choosing is normally 300-500ms+ (well clear of the guard), so this mostly affects players tapping fast/blind (e.g. muscle-memory "always pick leftmost" habits) — a narrow but real segment, and arguably some of exactly the behavior the guard exists to discourage, so this is a low/judgment-call severity item, not a regression to block on. If addressed, cheapest fix is probably not shortening the window (that reintroduces the mis-tap risk) but adding a lightweight rejected-tap cue (e.g. a brief `navigator.vibrate` tick or a subtle shake on the tapped card) so a fast player gets an explicit "not yet" signal instead of an unexplained no-op.

Low severity in practice — different UI regions (enemy-intent line vs. player HP bar), different visual forms (text vs. a bar fill), and different immediate context (enemy stat block vs. player stat block) mean the two are unlikely to actually be confused at a glance, so this is a polish note rather than a functional problem. - `beat:boss-telegraph mechanism:guard-pitch-contour` — low-priority nuance flagged by `game-dopamine-evaluator`'s qualitative pass, evaluated here from a presentation-correctness angle and considered worth tracking (not urgent): the `guard` cue's two-tone sequence is descending (262Hz → 196Hz), which in typical game-audio convention reads as "negative/fail" (e.g. a miss or death stinger — this game's own `playEndGameSting(false)` uses a descending sawtooth triple for death), while ascending tones read as "positive/success" (the win sting is ascending). `guard` means "safe, zero incoming damage this turn" — the opposite of what a descending contour conventionally signals — so on a player's *first* exposures (before they've learned by repetition that low+descending=guard=harmless here), the pitch direction alone could momentarily misread as bad news. Confirmed the color channel (`.intentAlert--safe` blue `#80d8ff` vs `.intentAlert--danger` red/orange `#ff6e40`) already disambiguates unambiguously and passes WCAG AA per `game-usability-tester`'s check, so this is not a blocker — just a case where the audio-alone signal fights the color-alone signal on convention. Suggested (cheap, no new dependencies): flip `guard`'s tone order to ascending (e.g. 196Hz→262Hz, same frequencies, reversed order) so both channels agree in the "safe" direction; verify `charge`'s existing 660→880 ascending order still reads as danger via its color tint doing the disambiguating work there instead (rising pitch is more ambiguous for danger than for safety, but charge already leans on its red tint + higher absolute pitch + square-wave harshness, so it's lower-risk as-is).

## game-human-playtester

- `last-checked: 2026-07-23T02:28:49Z`
- First run of this evaluator. Played 2 sessions with real per-turn judgment (not the fixed-formula bot): normal difficulty to floor 26-27 (died mid-run at 12/96 HP, stopped voluntarily to compare difficulties, still alive), hard difficulty through floor 11 (survived the floor-10 boss, stopped at 40/50 HP). Narrated reasoning throughout; findings below.
- `dead-cards: strike/defend/tower_shield become reliably skippable once a run has 2-3 hybrid dmg+block cards` — by roughly floor 12-15 on both difficulties, every reward screen offering only baseline `strike` (6dmg/1cost), `defend` (6block/1cost), or `tower_shield` (12block/2cost, same 6/cost rate as `defend`) felt like a non-choice: they're strictly worse-per-cost than cards already in a typical deck (`riposte` 4dmg+3block/1cost, `brace` 9block/1cost, `mist_cut` 6dmg+1block/1cost, `iron_wave` 6dmg+8block/2cost, `guard_up` 14block/2cost). Concretely hit reward screens on floors 15, 18, 21, 23 (normal run) where all 3 offered cards were dominated by cards already owned, and I used the skip button rather than dilute the deck. This isn't a single-card balance bug (each card is fine in isolation vs. the STARTER_DECK) — it's a structural pattern where the *early-game baseline cards keep reappearing in reward pools at mid-late floors* with no scaling/replacement, so their relative value decays hard as the hybrid-card pool fills up a deck. Worth a structural look (not a numeric tweak): consider having `REWARD_POOL` weight against offering cards a run already has 2+ copies of, or excluding pure-stat star-1 cards (`strike`/`defend`) from reward pools past a certain floor.
- `standout-combo: riposte + mist_cut/double_strike/iron_wave/brace (all 1-2cost hybrid dmg+block)` — once a run has 3+ of these, a very strong repeatable pattern emerges: play 2-3 of them in one turn to simultaneously fully block the (deterministic, pre-shown) non-boss enemy attack *and* deal solid damage, taking 0 net damage most turns while still killing the enemy in 2-3 turns. This felt great/satisfying the first few times but by floor ~20 became close to "the obvious play" every non-boss turn (just sum up hand block vs. shown enemy atk, play enough hybrids to clear it, spend the rest on damage) — reduces the density of genuinely hard decisions in the back half of a run. Contrast with early game (floors 1-10) where card/energy scarcity made every turn a real trade-off.
- `mechanic: random-event duplicate branch is a much bigger power spike than the remove branch` — confirmed both branches firing in both runs (event fires ~25% post-combat as documented). The remove branch (82% of events) is minor, low-tension deck thinning (I defaulted to removing a redundant `strike`/`defend` each time, an easy/obvious pick). The duplicate branch (18%) was a clearly-exciting, high-value moment each time it appeared — duplicating an already-strong star-3 card (`bash`, `fortress`, `mist_cut`) meaningfully snowballs a run's power in a way remove never does. Not necessarily a bug (`game.js`'s own comment already acknowledges duplicate is the stronger branch and rate-limits it to 18%), but flagging for `game-balance-tester` to verify the 82/18 split still feels right given how much more run-defining a duplicate felt in actual play vs. a remove.
- `beat: boss guard/charge telegraph produces genuinely good decision-quality` — the floor-10 hard-mode boss fight (ボスオーク, chained guard→charge→attack for 22dmg while I was at 16/50 HP) was the single best moment across both runs: the guard turn creates a real puzzle (attacks are 65% discounted but blocking is *free* since the boss won't hit that turn, so the correct play is "spend energy on damage anyway since it doesn't carry over" — non-obvious the first time), and the charge-then-double-attack telegraph gave enough advance warning (2 full turns) to stack `fortress`+`guard_up`+`defend` for exactly enough block, which felt earned rather than lucky. This is the game's high point for decision quality; worth protecting/not diluting when tuning boss AI further.
- `unfair-vs-earned: no unfair deaths observed, but one clear self-inflicted misplay` — at floor 26 (normal run) I misplayed a turn (played `bash`+`mist_cut` for damage but only 1 total block against a 7-atk hit, forgetting to include a block card) and took 6 needless damage, dropping 18hp->12hp (13%) with no boss/emergency in sight. This wasn't the game being unfair — full information was available (enemy intent always shown for non-boss enemies) and a block card was in hand; it was pure my-own-error. Notable because the moment *felt* like near-death/unfair from the inside until I re-examined the log, which suggests the UI's after-the-fact damage feedback doesn't make it easy to spot "you had the block available and didn't use it" — a soft argument for `game-feel-evaluator`'s existing near-lethal-severity backlog item (a distinct cue for drops into the danger zone would have made this misplay register immediately instead of silently).
- `reward/buff screen tension: genuinely mixed` — early game (floors 1-9) reward picks were consistently real dilemmas (e.g. floor-1 `brace` vs `finishing_blow` vs `shield_bash`, or hard-mode floor-1 `fortress` vs `shield_bash` vs `defend`) since the deck has few answers yet. Buff screens (floor 10/20, `vigor`/`renewal`/`insight`/`might`/`ward`) were consistently well-tuned tension: `renewal` is an obvious pick whenever HP is low (as designed, matches the bot's own heuristic), but when HP was healthy and no heal was offered (floor 20 normal run: `vigor` vs `insight` vs `ward`), the choice between a flat HP bump, a compounding draw buff, and a small recurring block was a genuine judgment call with no dominant answer — this screen is working as intended.
