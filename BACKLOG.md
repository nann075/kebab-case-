- `interaction-consistency: 250ms overlay-input-guard silently swallows sub-250ms real taps with no distinguishing feedback` — new finding this cycle (`armOverlayInputGuard`/`isOverlayInputGuarded`, `game.js` ~line 55-70, added to prevent the last-kill-tap from bleeding into the reward/buff/event overlay that pops in under the same coordinates). Verified via Playwright with real trusted `page.mouse.click()` (not synthetic `dispatchEvent`, which the guard correctly exempts via `e.isTrusted`): a single real tap on a reward card at 150ms or 200ms after the overlay appears is fully swallowed (no deck change, mode stays `reward`), while 250ms+ registers normally — the cutoff is exact and matches the `OVERLAY_INPUT_GUARD_MS` constant. The friction: a swallowed tap gives no dedicated feedback (no log line, no sound, no `navigator.vibrate`) — only the pre-existing `.card:active { transform: scale(0.96) }` CSS press-state, which fires on any pointerdown regardless of whether the JS handler acted on it, so a player whose first tap lands in the 150-200ms range experiences a card that visually depresses but does nothing, then has to tap again with no explanation why. Reaction-time context: genuinely reading 3 new cards and choosing is normally 300-500ms+ (well clear of the guard), so this mostly affects players tapping fast/blind (e.g. muscle-memory "always pick leftmost" habits) — a narrow but real segment, and arguably some of exactly the behavior the guard exists to discourage, so this is a low/judgment-call severity item, not a regression to block on. - `beat:boss-telegraph mechanism:guard-pitch-contour` — low-priority nuance flagged by `game-dopamine-evaluator`'s qualitative pass, evaluated here from a presentation-correctness angle and considered worth tracking (not urgent): the `guard` cue's two-tone sequence is descending (262Hz → 196Hz), which in typical game-audio convention reads as "negative/fail" (e.g. a miss or death stinger — this game's own `playEndGameSting(false)` uses a descending sawtooth triple for death), while ascending tones read as "positive/success" (the win sting is ascending). `guard` means "safe, zero incoming damage this turn" — the opposite of what a descending contour conventionally signals — so on a player's *first* exposures (before they've learned by repetition that low+descending=guard=harmless here), the pitch direction alone could momentarily misread as bad news. Suggested (cheap, no new dependencies): flip `guard`'s tone order to ascending (e.g. 196Hz→262Hz, same frequencies, reversed order) so both channels agree in the "safe" direction; verify `charge`'s existing 660→880 ascending order still reads as danger via its color tint doing the disambiguating work there instead (rising pitch is more ambiguous for danger than for safety, but charge already leans on its red tint + higher absolute pitch + square-wave harshness, so it's lower-risk as-is).

## game-human-playtester

- `last-checked: 2026-07-23T02:28:49Z`
- First run of this evaluator. Played 2 sessions with real per-turn judgment (not the fixed-formula bot): normal difficulty to floor 26-27 (died mid-run at 12/96 HP, stopped voluntarily to compare difficulties, still alive), hard difficulty through floor 11 (survived the floor-10 boss, stopped at 40/50 HP). Narrated reasoning throughout; findings below.
- `dead-cards: strike/defend/tower_shield become reliably skippable once a run has 2-3 hybrid dmg+block cards` — by roughly floor 12-15 on both difficulties, every reward screen offering only baseline `strike` (6dmg/1cost), `defend` (6block/1cost), or `tower_shield` (12block/2cost, same 6/cost rate as `defend`) felt like a non-choice: they're strictly worse-per-cost than cards already in a typical deck (`riposte` 4dmg+3block/1cost, `brace` 9block/1cost, `mist_cut` 6dmg+1block/1cost, `iron_wave` 6dmg+8block/2cost, `guard_up` 14block/2cost). Concretely hit reward screens on floors 15, 18, 21, 23 (normal run) where all 3 offered cards were dominated by cards already owned, and I used the skip button rather than dilute the deck. This isn't a single-card balance bug (each card is fine in isolation vs. the STARTER_DECK) — it's a structural pattern where the *early-game baseline cards keep reappearing in reward pools at mid-late floors* with no scaling/replacement, so their relative value decays hard as the hybrid-card pool fills up a deck. Worth a structural look (not a numeric tweak): consider having `REWARD_POOL` weight against offering cards a run already has 2+ copies of, or excluding pure-stat star-1 cards (`strike`/`defend`) from reward pools past a certain floor.
- `standout-combo: riposte + mist_cut/double_strike/iron_wave/brace (all 1-2cost hybrid dmg+block)` — once a run has 3+ of these, a very strong repeatable pattern emerges: play 2-3 of them in one turn to simultaneously fully block the (deterministic, pre-shown) non-boss enemy attack *and* deal solid damage, taking 0 net damage most turns while still killing the enemy in 2-3 turns. This felt great/satisfying the first few times but by floor ~20 became close to "the obvious play" every non-boss turn (just sum up hand block vs. shown enemy atk, play enough hybrids to clear it, spend the rest on damage) — reduces the density of genuinely hard decisions in the back half of a run. Contrast with early game (floors 1-10) where card/energy scarcity made every turn a real trade-off.
- `mechanic: random-event duplicate branch is a much bigger power spike than the remove branch` — confirmed both branches firing in both runs (event fires ~25% post-combat as documented). The remove branch (82% of events) is minor, low-tension deck thinning (I defaulted to removing a redundant `strike`/`defend` each time, an easy/obvious pick). The duplicate branch (18%) was a clearly-exciting, high-value moment each time it appeared — duplicating an already-strong star-3 card (`bash`, `fortress`, `mist_cut`) meaningfully snowballs a run's power in a way remove never does. Not necessarily a bug (`game.js`'s own comment already acknowledges duplicate is the stronger branch and rate-limits it to 18%), but flagging for `game-balance-tester` to verify the 82/18 split still feels right given how much more run-defining a duplicate felt in actual play vs. a remove.

This is the game's high point for decision quality; worth protecting/not diluting when tuning boss AI further.

Notable because the moment *felt* like near-death/unfair from the inside until I re-examined the log, which suggests the UI's after-the-fact damage feedback doesn't make it easy to spot "you had the block available and didn't use it" — a soft argument for `game-feel-evaluator`'s existing near-lethal-severity backlog item (a distinct cue for drops into the danger zone would have made this misplay register immediately instead of silently).
